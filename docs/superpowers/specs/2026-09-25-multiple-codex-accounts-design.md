# Multiple Codex Connections

## Intent and scope

Use two or more ChatGPT/Codex subscriptions as independently authenticated global providers. Existing routing profiles own only routes and pools; a pool member remains `<provider>/<model>@effort`. Preserve the existing `codex` provider name and all references. Do not deploy, restart, auto-switch profiles, or add a standby mode.

## Connection identity and credentials

A Codex provider has a persistent, randomly generated `auth_id` (`omitempty`) in `providers.json`. The existing provider named `codex` without an ID uses the legacy slot and existing `ROUTER_CODEX_AUTH_FILE` (default `~/.config/claude-router/codex-auth.json`); no copy or rewrite is needed, and repeated startup leaves routing and credentials unchanged. A newly created provider always gets a fresh ID, including one reusing a deleted name. Its token path is a private file in the legacy auth directory whose basename includes both a safely encoded provider name and the ID. Its store never reads the legacy file or a prior ID's file. Creating a provider does not import credentials; an explicit browser OAuth or CLI import writes the selected provider's file. Removing a provider leaves the auth file intact, never reuses its ID, and drops its model and route references by the existing global-provider removal rules. Codex rename is rejected in the UI; remove and recreate with explicit login instead. No auth tokens go into providers.json or the UI.

Each provider resolves to its own `codexAuthStore` and per-provider credential path. Copy `withFileLock` from deployment commit `091645c` verbatim; the auth store locks `path+".lock"` and re-reads disk during both expiry and rejected-token refresh (`refreshRejected` through `refreshLocked`) before writing, and locks import and OAuth completion. Keep lifecycle/quiesce guard out of this branch; deployment integration attaches it to all stores. Do not introduce a competing lock or broaden the OAuth token implementation. A single pending browser flow on the fixed callback port is acceptable, but it must retain its target provider ID and reject a different provider while pending. Deleting/recreating the name during login must not authorize the replacement with the old flow.

## Routing: failover pools

Network authorization, rejected-token refresh, catalog probing, and usage all select the auth store for the provider named on the candidate or UI action. Catalogs and usage caches are per provider and cannot mix accounts.

A pool has a type (Clarification 5). There are two types, `failover` and `balance`: `pool_settings.<pool>.type` is `"failover"`, `"balance"` or absent, and absent means failover, so existing files need no migration and are not rewritten. Any other value is rejected by `validate()`; a hand-edited file with it is not applied and the settings page shows the reload error (see Dashboard). A UI save of pool settings keeps the stored type. The second type, `balance`, is described in "Routing: balance pools" below; everything in this section applies to both types except the choice of a new session's first member.

In a failover pool, a new session goes to the first member in pool order that is not cooling; members in cooldown go last, ordered by `CoolUntil`. EWMA score, first-byte latency, in-flight load and the pool's `balance` field do not change this order. Codex members get no background probes, so a rating order could keep a recovered first connection behind the second forever; in failover order it leads new sessions again as soon as its cooldown ends. The session is then bound by the existing 24-hour affinity: it stays on the same provider and model while that member is healthy, even when it is busy. A 429 or other existing retryable failure moves the request to the next member in pool order, and the binding moves with it; the session stays there and does not return when the first member recovers. A recovered first member gets only new sessions. When all members return 429, keep the existing behavior: cooldown 20 seconds × 2^n (capped as today), candidates in cooldown ordered by `CoolUntil`, HTTP 429 to the client, and the session pinned to the last attempted member. The pool's failover checkbox keeps its meaning: with it off, a failed request is not retried on the next member. Existing no-background-probes-for-Codex rule remains.

The numeric `balance` field leaves the pool form; its stored value is kept on every save and has no effect in pool routes. Live pools have one member each, so live routing is unchanged; only pools with several members move from rating order to pool order. Routes that are not pools (a direct model route), the health checker and the dashboard ranking keep the rating order with `balance`.

## Routing: balance pools

`pool_settings.<pool>.type = "balance"` is set explicitly on a pool. It changes only which member a new session starts on; everything else is failover. Connections (providers) are compared, never models of one connection: each connection is represented by its first member in pool order that is not cooling, and the models of one connection keep pool order. The score is the number of live session bindings of this pool on that connection, counted from the bindings under the health lock in the same critical section that records the new binding, so concurrent new sessions see each other. The lowest score wins and a tie keeps pool order. The criterion is one replaceable function, so a criterion by the account's remaining limit would replace only it. A bound session keeps its member while it is healthy; on failure it moves as in failover and stays there. A request without a session is not balanced. The type is read from the current config snapshot on every request, so a form save or a settings reload switches it without a restart and without clearing bindings; only new sessions follow the new type.

A signed-out Codex member (no credential, or a token the issuer rejected) is skipped for new and bound sessions until the next sign-in or import, and a sign-in failure during a request moves it to the next member; when every member is signed out, the client gets the sign-in error. A client cancel (Esc, closed connection) is not a member failure: no failure is recorded and the session is not moved.

## Dashboard and migration

Provider cards and connection details show their own login/import status and usage; `/settings/codex/*` actions take an explicit provider name, verify that name against the current config, and target that provider only. Usage refresh is a button for that connection, with no network usage query on page load. Provider names on forms are verified against current config before writing. Existing `codex` keeps its model catalog, profile routes and pool members; the pre-existing `codex` with no `auth_id` always maps to the legacy file, while any newly created `codex` has a fresh ID. A legacy configuration needs no metadata rewrite; if a one-time startup migration must assign an ID to a pre-existing non-`codex` Codex provider, first back up `providers.json`, write atomically, and avoid rewriting unchanged files. After startup, reject any hot-reloaded/manual `providers.json` with a non-`codex` Codex provider missing `auth_id` in `validate()`, with an explicit error in the log and settings UI; never auto-rewrite the manually edited file or infer an ID. The config watcher retains only the latest per-settings-file reload error text and timestamp in memory, while the previously applied snapshot remains active. The settings page shows `file not applied: <error>; snapshot from <time>` until a successful reload clears the banner; it stores no error history or disk state. Never infer credentials from an orphaned token file. Auth files left after deletion accumulate and require manual cleanup (document this).
