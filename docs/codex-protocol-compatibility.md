# Совместимость с Codex Responses

Эталон: официальный [openai/codex, `985cf47a4eb6084b2ff6b30ebdb1216acda85bb4`](https://github.com/openai/codex/tree/985cf47a4eb6084b2ff6b30ebdb1216acda85bb4), проверен 27 сентября 2026 года.
Область проверки — транспорт Responses, которым пользуется адаптер роутера.
Совпадение исходных контрактов само по себе не доказывает полноту адаптера или
совместимость с закрытой серверной реализацией ChatGPT.

## Как часто меняется upstream

Локальная официальная копия содержит **shallow history**. Доступное окно этой
проверки: после `b9852fe6f7c73c98277da38cccb238083c843d4e` (10 сентября)
до `985cf47a4eb6084b2ff6b30ebdb1216acda85bb4` (27 сентября 2026 года).
В нём **37 коммитов в 13 разных календарных датах** затронули хотя бы один из:

- `codex-rs/codex-api/src/common.rs`;
- `codex-rs/codex-api/src/sse/responses.rs`;
- `codex-rs/codex-api/src/sse/responses_error.rs`;
- `codex-rs/core/src/client.rs`;
- `codex-rs/protocol/src/models.rs`.

Граничный shallow-коммит исключён: Git показывает его как добавление всех
существовавших файлов. Это **37 изменений исходников, не 37 нарушений обратной
совместимости**; сюда попадают рефакторинг, тесты и телеметрия. По этому короткому
окну нельзя вывести долгосрочный график релизов или частоту breaking changes.
Однако существенные для адаптера изменения происходят несколько раз в неделю:

| Дата | Подтверждённое изменение | Значение для роутера |
|---|---|---|
| 11 сентября | [Cache affinity для ephemeral forks](https://github.com/openai/codex/commit/bc5957eac9e89e66f990ed490d11e625a4a3b02c) | В ChatGPT привязка кэша зависит от `session-id`; одного JSON `prompt_cache_key` недостаточно для повторения поведения клиента. |
| 15 сентября | [Изображения по `file_id`](https://github.com/openai/codex/commit/7b8b17b97a5f08f088852e8bc9ae388cff38c714) | Расширен wire-тип входных изображений и результатов инструментов. |
| 23 сентября | [Числовой `reasoning.effort`](https://github.com/openai/codex/commit/ae132dc50ab5d8214a8fe599c3c1cfbb5f2ef186) | Числовое пользовательское значение сериализуется числом JSON, именованные значения остаются строками. |
| 24 сентября | [Отдельная terminal error для Flex capacity](https://github.com/openai/codex/commit/dafb133c5b7f6a95d77c7c0d288e86793c7cb937) | Ошибки потока нельзя обрабатывать как успешный пустой ответ. |
| 26 сентября | [WebSocket continuation при steering](https://github.com/openai/codex/commit/12de0e395d3313bc564190d983cb4f5acf0be713) | Продолжение ответа зависит от состояния транспорта; совпадение JSON-полей не означает поддержку WebSocket. |

Подсчёт воспроизводится без сети:

```sh
git -C /path/to/codex rev-parse --is-shallow-repository
git -C /path/to/codex log \
  b9852fe6f7c73c98277da38cccb238083c843d4e..985cf47a4eb6084b2ff6b30ebdb1216acda85bb4 \
  --format='%h %cs %s' -- \
  codex-rs/codex-api/src/common.rs \
  codex-rs/codex-api/src/sse/responses.rs \
  codex-rs/codex-api/src/sse/responses_error.rs \
  codex-rs/core/src/client.rs \
  codex-rs/protocol/src/models.rs
```

## Детектор изменений контракта

`internal/protocolcheck/baseline.json` содержит pinned revision и SHA-256 для
31 выбранного контракта: схем запроса/элементов/результатов инструментов,
SSE-декодера и terminal errors, HTTP endpoint, session headers, функций сборки
запроса, reasoning и cache/session affinity. Большой `core/src/client.rs`
целиком не хешируется: проверяются конкретные функции и константы заголовков.
Для небольших файлов wire-слоя проверяется весь файл или часть до модуля тестов.

```sh
go build -o /tmp/codex-protocol-check ./cmd/codex-protocol-check
/tmp/codex-protocol-check -codex /path/to/codex
/tmp/codex-protocol-check -codex /path/to/codex -json
```

| Результат | Код возврата | Значение |
|---|---|---|
| `match` | 0 | Все выбранные исходные контракты совпадают с проверенным эталоном. |
| `drift` | 1 | Хотя бы один выбранный контракт изменился; требуется ревью и проверка адаптера. |
| `unknown` | 2 | Не удалось прочитать файл, найти однозначную границу или проверить manifest. Совместимость не установлена. |

При сочетании drift и unknown общий статус — unknown, а отдельные результаты
сохраняются в отчёте. Отсутствующие файлы, переименованные символы и новые версии
manifest никогда не превращаются в зелёную проверку. CLI не использует токены,
не отправляет inference-запросы, не обновляет checkout или эталон и не запускает
код из проверяемого репозитория. Чтение ограничено указанной директорией,
включая переходы по symlink.

Это консервативный detector изменений исходников, а не Rust AST-анализатор:
он использует однозначные rustfmt-границы деклараций, включает `serde`-атрибуты
и нормализует только CRLF. Изменение комментария или форматирования внутри
контракта также требует ревью. Правки UI вне выбранных функций не влияют на
результат. Новое поле или вариант внутри выбранной схемы, новая SSE-ветка или
изменение сериализации дают drift; перемещение реализации даёт unknown.

Детектор не видит изменения закрытого backend без соответствующих изменений
официального клиента, поведение в непокрытых файлах, всю семантику WebSocket
или все новые возможности Codex. Его используют вместе с регрессионными
тестами адаптера и явной матрицей поддерживаемых возможностей.

## CI и пересмотр эталона

`.github/workflows/codex-protocol.yml` выполняет тесты детектора и адаптера,
загружает официальный Codex на pinned revision и проверяет воспроизводимость
эталона при профильных PR и push. Ежедневно в **06:23 UTC (09:23 Москвы)** и
по `workflow_dispatch` дополнительно проверяется актуальный `openai/codex:main`.
Drift и неизвестный результат завершают CI с ошибкой и перечисляют контракты.
Workflow не создаёт issues, не отправляет сообщения и не меняет эталон.

Расписание начнёт работать после появления workflow в default branch GitHub.
GitHub может задержать плановый запуск; это проверка CI, не фоновый сервис
локального роутера. Отдельный локальный read-only запуск доступен сразу.

При срабатывании:

1. Зафиксировать SHA проверяемого upstream и прочитать diff указанных контрактов
   относительно `revision` в manifest.
2. Отделить изменения wire/семантики от рефакторинга; обновить адаптер и добавить
   сценарий регрессии для нового поведения либо записать обоснованное ограничение.
3. Прогнать тесты адаптера и детектора. Для сетевой проверки достаточно отдельного
   явно разрешённого сценария; CI не должен расходовать подписку.
4. Только после ревью вручную обновить нужные `sha256`, `revision`, `reviewed_on`
   и, если upstream перенёс код, селекторы. Новый hash есть в отчёте drift;
   у детектора намеренно нет режима автоматического принятия нового эталона.
5. Проверить match с новым pinned checkout. Смена эталона не заменяет тестов.

## Матрица адаптера

Роутер переводит Anthropic Messages от Claude Code в подписочный **Responses
HTTP/SSE**. Это транспорт генерации; он не реализует Codex app-server, локальные
встроенные инструменты Codex или WebSocket steering. HTTP остаётся отдельным
поддерживаемым путём официального клиента. Неизвестный завершённый тип output
явно отклоняется, чтобы новый серверный результат не превратился в пустой успех;
необязательные неизвестные SSE-события игнорируются, как в официальном клиенте.

| Поведение | Реализация и проверяемое требование |
|---|---|
| Обычный и потоковый ответ | Общий native decoder, корректные границы SSE, CRLF, многострочный data, отказ модели, terminal error/EOF. |
| Ответ без текстовых delta | Текст берётся из `output_item.done` или `response.completed.output`; уже показанный префикс не повторяется. |
| `end_turn=false` / interrupted | Дополняем native input завершёнными items и продолжаем; после function call ждём результат инструмента от клиента. Есть предел продолжений и защита от повторного response ID. |
| Состояние рассуждения | Сохраняются исходные items: encrypted reasoning, item/call IDs, phase и непрозрачные метаданные. Клиенту они не выдаются как Anthropic signatures. |
| Повторное использование состояния | Только одинаковые account, provider/model, session и полный видимый префикс. Изменённые сообщения/аргументы и смена аккаунта не импортируют чужой state. |
| Хранение | Приватный `codex-state/` рядом с credentials: отдельный JSON snapshot на scope, atomic write и блокировка. Это состояние активного диалога, независимое от очистки/вытеснения журнала UI. Каталог 0700, файлы 0600, предел snapshot 64 MiB; переполнение или повреждение дают явную ошибку. |
| Привязка кеша | Стабильные обезличенные `prompt_cache_key`, `session-id`, `thread-id`; полученный `x-codex-turn-state` сохраняется в пределах одного tool-turn и сбрасывается для следующего сообщения пользователя. |
| Инструменты | Function call/результат, JSON object arguments, параллельные вызовы с учётом клиентского запрета, структурированные результаты с изображениями. |
| Ошибки и отмена | Client cancellation и ошибка записи закрывают upstream. Ошибка после начатой генерации или предыдущего внутреннего продолжения не повторяет весь запрос на другом аккаунте. Чистое отклонение до генерации может использовать существующий failover. |
| Usage | Сохраняются cached/write/reasoning counts; в статистике суммируются внутренние вызовы, клиент получает usage последнего контекста. Отсутствующая статистика отличается от явного нуля. |
| Заголовки/OAuth | HTTPS endpoint закреплён, redirects запрещены; смена аккаунта проверяется перед отправкой и после refresh. |

Сценарии находятся в `internal/providers/codex/*_test.go`,
`codex_protocol_integration_test.go`, `codex_protocol_review_test.go`,
`local_codex_test.go` и тестах перевода usage. Они работают на записанных
структурах/локальных HTTP fixtures и не делают платных inference-запросов.
Проверка исходников и этих сценариев не заменяет наблюдение реальной статистики
после установки: исторические записи без cache metadata восстановить нельзя.

## Показатели подключения и сессии

Карточки показывают измерения из сохранённой истории за 24 часа: все входные,
прочитанные из кеша, входные без кеша и выходные. Выходные уже включают reasoning;
запись нового кеша относится к входным без cache read. Процент считается только
по запросам с известными cache metadata, отдельно показано покрытие измерениями.
Это не формула списания подписки: точную стоимость единиц лимита эти счётчики
не сообщают. Вызовы вне роутера в статистику не входят.

Мягкий сигнал низкого кеширования требует достаточной серии крупных запросов
одной сессии к одной модели: пять измерений после начального запроса, суммарно
от 100 тысяч входных токенов и менее 20% cache read. Смена аккаунта или разрыв
достоверной серии снимают прежнее предупреждение. Противоречивые счётчики
отмечаются отдельно и исключаются из сумм. Оба сигнала предлагают проверить
расход, а не объявляют доказанную поломку серверного кеша.
