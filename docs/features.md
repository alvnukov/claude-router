# claude-router: функциональный обзор

Назначение: безопасно переключать модели под Claude Code, видя полную картину лимитов и расхода (сейчас она неполная, см. разделы 9–11).
Для Claude Code роутер прозрачен: он выглядит как API Anthropic и сам решает, куда отправить запрос.

Состояние на 2026-09-25: origin/main 8f60c02 (окна лимитов Anthropic и Codex в `/api/limits`, автообновление лимитов Codex) вместе с несколькими подключениями Codex и типами пулов. Ссылки `файл:строка` указывают на код этого изменения; в разделе 14 — на 1cd4eec, деплой blue/green. Исключение — ссылки на `router`, `internal/cli/` и `main.go:341`: они указывают на код после переноса команд службы в бинарь.
Запущенный бинарь может быть собран из более старого коммита; `./router restart` пересобирает его. На f11cb64 так и было: `GET 127.0.0.1:8788/api/limits` отвечал 404; позже не проверялось.

## Как устроено

- Один процесс `localrouter` (Go), `./router build` собирает его в `$ROUTER_HOME/localrouter` (`router:24`).
- Два HTTP-порта: API-прокси `ROUTER_LISTEN`=127.0.0.1:8787 (`main.go:87,209`) и UI `ROUTER_UI_LISTEN`=127.0.0.1:8788; пустое значение выключает UI (`main.go:96,205-208`).
- Фоновые задачи: каждые 2 с перечитывает `env` и `providers.json` (`main.go:195`, `settings.go:174-198`), проверяет модели пулов (`checker.go:20`), раз в час обновляет каталоги (`catalog.go:110-129`), раз в 10 мин — лимиты Codex (`codex_usage.go:320-385`). На время входа в Codex слушает 127.0.0.1:1455 (`codex_oauth.go:22,63`).
- Состояние лежит рядом с бинарём, в `ROUTER_HOME` (по умолчанию `~/.claude/local-router`): `env`, `providers.json` (+ `providers.json.profiles/`, `providers.json.active-profile`, резервные копии `.before-*`), `models.json` (рейтинги), `history.jsonl`, `limits.json` (+ `.lock`), `router.log`, `router.pid` (`internal/cli/service_cmd.go:168-178,324-337`, `providers.go:63-71`, `health.go:60-68`, `history.go:16-24`, `limits.go:179-187`).
- Вне `ROUTER_HOME` лежат `~/.config/claude-router/codex-auth.json` (`codex_auth.go:59-62`) и `~/.claude/settings.json` с `settings.json.router-proxy-backup` (`claude_proxy.go:35-45`).
- Бинарь сам читает `env` при старте (`settings.go:118-135`). Адреса и upstream читаются только при старте (`settings.go:160-163`).

## 1. Перехват Claude Code (ANTHROPIC_BASE_URL)

- **Что делает:** по кнопке записывает адрес роутера в `env.ANTHROPIC_BASE_URL` пользовательского `settings.json` и сохраняет прежнее значение в `settings.json.router-proxy-backup` (0600, атомарно). Обратная кнопка возвращает прежнее значение или удаляет ключ, а правки, сделанные с тех пор в файле, сохраняет. Восстановление отказывается, если значение уже изменили вне роутера; любая запись отказывается, если файл поменялся во время записи (`claude_proxy.go:146-227`, проверки `:182-183,203-209`). Симлинк на `settings.json` сохраняется (`claude_proxy.go:68-72`). То же включение без UI: `./router env` пишет адрес тем же кодом, с той же резервной копией, и печатает `ANTHROPIC_BASE_URL=<адрес>`; адрес — `ROUTER_LISTEN` из `env`, иначе 127.0.0.1:8787 (`internal/cli/service_cmd.go:307-313`, `main.go:341`). Второй способ: `claude-local` задаёт переменную только своему процессу `claude` и сначала запускает роутер, если тот не отвечает (`claude-local:16-22`).
- **Где настраивается:** UI `/settings`, карточка «Claude Code»: «Подключить Claude к роутеру» и «Восстановить настройки Claude»; включить можно и командой `./router env`, выключить — только кнопкой. Каталог задаёт `CLAUDE_CONFIG_DIR` (`claude_proxy.go:36`), адрес берётся из `ROUTER_LISTEN`, при этом 0.0.0.0 заменяется на 127.0.0.1 (`claude_proxy.go:47-62`).
- **Код:** `claude_proxy.go:260` (`settingsClaudeProxy`), `claude_proxy.go:146` (`set`).
- **UI/API:** `POST /settings/claude-proxy`, `op=connect|restore` (`ui.go:132`).
- **Ограничения:** включается и выключается только вручную. Роутер не трогает `settings.json` ни при старте, ни при остановке, ни при падении: обработки сигналов в `main` нет (`main.go:184-212`), поэтому адрес продолжает указывать на 8787. Процесс заново поднимает launchd (`internal/cli/service_cmd.go:168-178`), а без агента связь пропадает до ручного восстановления. Что делает Claude Code, когда адрес недоступен, — не проверено. Изменение действует после перезапуска Claude Code (`claude_proxy.go:278`); по подсказке в UI, настройки проекта могут его переопределить (`ui/settings.html:194`). Журнала изменений нет: `claude_proxy.go` ничего не пишет в `router.log` (пакет `log` не импортирован, `:3-13`), хранится только последняя резервная копия, и восстановление её удаляет (`:221-225`). `claude-local` требует файла `env` с `ROUTER_LISTEN` (`claude-local:7,16,20`).

## 2. Проксирование в облако Anthropic

- **Что делает:** если маршрут запроса к `/v1/messages` — «Anthropic», обратный прокси отправляет в `ROUTER_UPSTREAM_URL` то же тело байт в байт и заголовки клиента (`Authorization`/`x-api-key`, `anthropic-*`, `User-Agent`), а ответ стримит без буферизации (`main.go:215-233,278-287`). Учётные данные роутер не добавляет и не подменяет. Все прочие пути, кроме служебных, проксируются так же, без проверки маршрута. На каждый такой запрос в `router.log` пишется строка `pass <метод> <путь> -> <статус> in <длительность>`: путь без query, экранированный и обрезанный до 256 байт, без заголовков и тел; 502 — upstream недоступен (`main.go:315-329`).
- **Что меняется в запросе:** `Host` переписывается на хост upstream (`main.go:231`). При включённом UI удаляется `Accept-Encoding`, чтобы история видела несжатое тело (`main.go:279-285`). Стандартный `httputil.ReverseProxy` убирает hop-by-hop заголовки и добавляет `X-Forwarded-For: 127.0.0.1`.
- **Где настраивается:** `ROUTER_UPSTREAM_URL`, по умолчанию `https://api.anthropic.com` (`main.go:71`), читается только при старте. Маршрут «Anthropic» задаётся в `/settings#routes`.
- **Код:** `main.go:214` (`newMainHandler`): `/v1/messages` `:244-290`, `count_tokens` `:292-309`.
- **UI/API:** 127.0.0.1:8787 `/v1/messages`, `/v1/messages/count_tokens`, `GET /healthz` → `ok` (`main.go:311-313`). Остальные пути уходят в upstream.
- **Ограничения:** маршрут «Не настроено» даёт 400 `invalid_request_error` без обращения к провайдеру (`main.go:175-180,273-275`), а у новой установки маршрутов нет вообще (`providers.go:444,551-562`). Нет соединения с upstream — ответ 502 `upstream unreachable` без повторов и без запасного пути (`main.go:216-219`). Для маршрутов, которые ведут не в Anthropic, `count_tokens` возвращает оценку `len(body)/4` (`main.go:305-308`). Запросы вне `/v1/messages` в историю не пишутся, от них остаётся только строка `pass` в `router.log`.

## 3. Локальный маршрут и подписка Codex

- **Что делает:** запросы с маршрутом «модель» или «пул» переводит из Anthropic Messages в формат OpenAI (`translate.go:152`) и отправляет либо в OpenAI-совместимый провайдер (`{base_url}/chat/completions`, `Bearer api_key`), либо в подписку Codex (`https://chatgpt.com/backend-api/codex/responses`) (`local.go:226-254`). Запросы к Codex идут без состояния на сервере (`store:false`, всегда `stream`) (`codex.go:33-98`). Ответ переводится обратно в SSE или JSON Anthropic (`local.go:395,489`). Учётные данные Anthropic провайдерам не передаются (`local.go:54-56,238-251`).
- **Несколько подключений:** каждый провайдер типа Codex — отдельная подписка со своим входом, файлом токена и каталогом моделей (`codex_stores.go:15-19`). Исходный `codex` без `auth_id` хранит учётную запись в `codex-auth.json`; остальные получают `auth_id`, их файл лежит рядом: `codex-auth-<hex имени>-<auth_id>.json` (`codex_stores.go:23-32`). Codex без `auth_id` под другим именем, повтор `auth_id` и `auth_id` у не-Codex файл провайдеров отвергает (`providers.go:138-152`). Действия `/settings/codex/*` называют подключение полем `provider`; без него или с чужим именем — 400 (`ui.go:529`).
- **Вход в Codex:** OAuth PKCE через браузер с колбэком на 127.0.0.1:1455, на вход даётся до 15 мин (`codex_oauth.go:53-91,131-196`). Другой способ — явный импорт входа Codex CLI из `$CODEX_HOME/auth.json` в выбранное подключение (`codex_auth.go:237-252`); автоматически CLI не читается. Учётная запись хранится в файле подключения (0600, атомарная запись) (`codex_auth.go:210-235`). Токен отправляется только на `https://chatgpt.com/backend-api/codex/*` (`codex_auth.go:280-283`).
- **Обновление токена:** выполняется перед запросом, если access-JWT истекает в ближайшие 30 с (`codex_auth.go:98-104,141-184`). На ответ 401 роутер один раз обновляет отвергнутый токен и один раз повторяет запрос. Если тот же токен отвергнут снова в течение минуты, сразу возвращается «сессия Codex недействительна» (`codex_auth.go:325-391`).
- **Блокировка:** загрузку, обновление и запись файла сериализует мьютекс внутри процесса (`codex_auth.go:38-49,87-105`). Обновление токена, вход и импорт вдобавок берут `flock` на `<файл>.lock` (`filelock.go:12`, `codex_auth.go:107-121,244`, `codex_oauth.go:185`); перед обновлением файл перечитывается, и токен, уже обновлённый другим процессом, берётся с диска. Файл читается один раз за жизнь процесса (`codex_auth.go:90-96`), поэтому внешняя правка видна только после перезапуска, входа, импорта или обновления токена. Работа двух процессов роутера с одним файлом — не проверено.
- **Где настраивается:** `/settings#connections`, тип провайдера OpenAI или Codex; у Codex адрес фиксирован и ключа нет (`providers.go:131-137`). Вход — `/settings#codex-subscription`, по блоку на подключение; импорт из CLI — в панели провайдера. Переменные: `ROUTER_CODEX_AUTH_FILE` (путь исходного файла; файлы остальных подключений лежат рядом), `CODEX_HOME`.
- **Код:** `local.go:57` (`handleLocal`), `local.go:226` (`tryModel`), `local.go:38` (`withoutSignedOut`), `codex_stores.go:19` (`codexStoreFor`), `codex_auth.go:87` (`credentialFor`), `codex_oauth.go:53` (`startCodexBrowserFlow`), `codex_context.go:11`.
- **UI/API:** `POST /settings/codex/login`, `POST /settings/codex/import`, `GET /settings/codex/status`, все с `provider` (`ui.go:138-140`).
- **Ограничения:** член пула, чьё подключение Codex вышло из аккаунта (нет файла или токен отвергнут), пропускается; если вышли все, клиент получает ошибку входа (`local.go:35-51,89`). Проверка входа не ждёт замка: подключение, чей токен в этот момент загружается или обновляется, считается вошедшим и остаётся кандидатом, а отказ, если он будет, обнаружит сам запрос (`codex_auth.go:264-282`). Ошибка входа Codex (401) — сбой, и запрос уходит к следующему члену (`local.go:282-283,307-310`); 401 от OpenAI-совместимого провайдера — ошибка ключа, запрос не переключается. Переименовать подключение Codex нельзя: удалить, добавить и войти заново. Файл удалённого подключения остаётся на диске, удалять вручную. Для `tool_result` без парного вызова роутер ищет этот вызов в истории той же сессии; если его нет, например после вытеснения из буфера истории, запрос отклоняется (`codex_context.go:11-50`). Блоки thinking из прошлых ответов при переводе отбрасываются (`translate.go:222`).

## 4. Маршрутизация по семейству модели и effort

- **Что делает:** из запроса берёт `model` и `output_config.effort`; пустой effort считается `default` (`main.go:165-182`). Сначала ищет точное правило версии `routes[model][effort]`, затем правило семейства `family_routes[семейство][effort]`, а если нет ни того, ни другого — «Не настроено» (`providers.go:551-562`). Семейство выводится из ID регулярным выражением (`families.go:10-19`), поэтому новые версии, например `claude-opus-5-5`, наследуют правила семейства. Режимы: `disabled`, `anthropic`, `model` — один `provider/model` с фиксированным effort и без failover (`main.go:134-136`), `pool` (`main.go:137-145`). Целевой effort передаётся как `reasoning_effort` или, для Codex, `reasoning.effort` (`local.go:102-106`, `codex.go:37-41`).
- **Где настраивается:** `/settings#routes`: карточки семейств, «Версии моделей и индивидуальные настройки» (наследовать или задать явно), «Добавить другую модель Anthropic». В файле профиля — ключи `family_routes` и `routes`.
- **Код:** `providers.go:551` (`routeFor`), `main.go:123` (`forModel`), `ui.go:745` (`settingsRoute`).
- **UI/API:** `POST /settings/route` (`ui.go:134`).
- **Ограничения:** effort Claude бывает только `default|low|medium|high|xhigh|max` (`providers.go:272-278`). Ненастроенный effort не переходит на соседний, неявного отката в Anthropic или в другой пул нет. Пустой пул даёт 400 (`main.go:178-180`).

## 5. Пулы и их настройки

- **Что делает:** пул — именованный упорядоченный список `provider/model`, у каждого члена свой целевой effort (`providers.go:35-38`). Кандидаты идут в порядке пула, рейтинг порядок не меняет; модели на паузе после сбоя (cooldown) идут в конец, раньше других та, что вернётся первой (`health.go:237-248`).
- **Тип пула:** `failover` (по умолчанию; поле `type` не задано — тоже failover) — новая сессия идёт к первому здоровому члену по порядку. `balance` задаётся явно и отдаёт новую сессию подключению, у которого меньше всего сессий этого пула; подключение представляет его первый член не на паузе, при равенстве решает порядок пула (`affinity.go:24-65,112-114`). Другие значения отвергаются (`pool_settings.go:62-66`). Тип меняется на лету из формы или файла и действует на новые сессии (`main.go:139-144`). Числовое поле пула `balance` устарело: при чтении игнорируется с одной строкой в логе и больше не пишется (`pool_settings.go:31-45`). Окно по рейтингу вне пулов задаёт только глобальная `ROUTER_LOCAL_BALANCE`.
- **Failover:** если до первого полезного события истёк таймаут, оборвалось соединение или пришёл HTTP 404/408/429/5xx, запрос уходит к следующему члену пула (`local.go:154-168,304-313`). После начала ответа модель не меняется, сбой лишь снижает её рейтинг (`local.go:172-194`). При `failover`=0 делается одна попытка у первого кандидата после сортировки, выбора типа пула и привязки сессии (`local.go:89-95`); маршрут «модель» всегда без failover (`main.go:134-136`).
- **Где настраивается:** `/settings#pools`: состав (добавить, убрать, ↑↓, effort) и форма «Сессии и таймауты». В файле профиля ключи `model_pools` и `pool_settings` (`pool_settings.go:21-27`): `type`, `failover`, `first_byte_seconds` (ожидание первого полезного SSE-события `stream_start.go:22`, для обычного ответа — первого байта, 0 — без лимита), `probe_seconds`, `max_input_chars` (обрезка контекста, `trim.go:31`, `local.go:73-81`). Пул без сохранённых настроек получает значения `ROUTER_LOCAL_*` из `env` (`pool_settings.go:47-52,97-110`).
- **Код:** `main.go:137-161`, `local.go:84-200`, `health.go:226` (`pick`), `affinity.go:42` (`balanceFirst`), `pool_settings.go:54` (`apply`).
- **UI/API:** `POST /settings/pools`, `op=create|delete|add|remove|up|down|effort` (`ui.go:1071-1145`); `POST /settings/pool-settings` (`ui.go:692-718`). Под каждым членом пула — строка его здоровья из раздела 7 (`ui/settings.html:36`, данные `ui.go:583`).
- **Ограничения:** пул, на который ссылается маршрут, удалить нельзя (`ui.go:1091-1098`). Effort члена проверяется по каталогу модели (`ui.go:1147-1170`). Одна модель входит в пул не больше одного раза (`providers.go:216-220`). `balance` считает сессии только внутри своего процесса и только по привязкам в памяти; запрос без `session_id` распределением не учитывается.

## 6. Профили

- **Что делает:** профиль — именованный набор правил: `family_routes`, `routes`, `model_pools`, `pool_settings` (`profiles.go:13-18`). Провайдеры, модели и каталог общие для всех профилей. Правки маршрутов и пулов сразу сохраняются в активный профиль (`profiles.go:41-50`, `settings.go:307-349`). Переключение действует со следующего запроса и сбрасывает привязки сессий (`profiles.go:228-256`). При первом запуске текущая настройка становится профилем `default`, а прежний файл сохраняется как `.before-profiles` (`profiles.go:165-198`).
- **Где настраивается:** `/settings#profiles`: «Клонировать активный», «Создать пустой», переключение, удаление неактивного. Файлы — `providers.json.profiles/<имя>.json` и указатель `providers.json.active-profile` (`profiles.go:148`, `providers.go:320-347,378-384`). Ручная правка подхватывается за 2 с (`settings.go:188-198`, `profiles.go:293-312`).
- **Код:** `profiles.go:200` (создать), `:228` (активировать), `:258` (удалить).
- **UI/API:** `POST http://127.0.0.1:8787/api/profiles/{name}/activate` возвращает `{"active_profile":"…"}`, а на неизвестное имя — 400 (`main.go:236-242`, `profile_http.go:9-17`). Тот же путь есть на UI-порту (`ui.go:127`). Формы: `POST /settings/profiles`, `/settings/profiles/activate`, `/settings/profiles/delete` (`ui.go:128-130`).
- **Ограничения:** активный и последний профиль удалить нельзя (`profiles.go:265-270`). Автоматического переключения, например по остатку лимита, нет: активация вызывается только из UI или API (`profile_http.go:11,25`). Когда удаляют модель, ссылки на неё чистятся и в неактивных профилях (`profiles.go:89-120`).

## 7. Здоровье и рейтинг моделей

- **Что делает:** для каждой `provider/model` ведётся `modelStat` (`health.go:27-42`): score — экспоненциальное скользящее среднее (EWMA) успехов с α=0.25; TTFB — EWMA времени до первого полезного события; пауза после сбоя (cooldown) — 20 с, удваивается до 5 мин (`health.go:20-25,123-162`). Счётчики: `failovers` — сколько раз запрос ушёл с модели, `served_after` — сколько раз модель подхватила запрос после чужого сбоя (`health.go:164-170`, вызов `local.go:165`). Фоновые проверки: моделям пулов без трафика дольше `probe_seconds` уходит `ping` на 1 токен; модель из нескольких пулов проверяется по самому короткому интервалу; модели Codex не проверяются (`checker.go:20-124`).
- **Где настраивается:** `probe_seconds` в настройках пула. Файл — `models.json` (`ROUTER_MODELS_STATE`; при пустом значении состояние хранится только в памяти) (`health.go:60-68`).
- **Код:** `health.go:123` (`note`), `health.go:226` (`pick`), `checker.go:20` (`startChecker`).
- **UI/API:** одна строка на модель, общий шаблон `model-stats` (`ui/settings.html:181-183`): ответы и сбои, сбоев подряд, рейтинг (score в %), первый байт (TTFB), пауза с остатком или «доступна», «ушла дальше» (`failovers`) и «подхватила» (`served_after`), фоновые проверки успех/сбой, давность последнего успеха, последняя ошибка. Строка стоит под каждым членом пула в `/settings#pools` (`ui/settings.html:36`) и под каждой моделью в `/settings#connections` → «Каталог добавленных моделей» (`ui/settings.html:77`). Данные — копия `modelStat` под мьютексом (`health.go:299`, `snapshot`), процент и TTFB считают `ScorePct` и `TTFB` (`health.go:46-47`). Эндпоинт сброса — `POST /settings/models op=reset` (`ui.go:1553-1555`).
- **Внутри пула:** рейтинг не задаёт порядок членов, его задаёт порядок пула; пауза после сбоя по-прежнему отправляет члена в конец (`health.go:237-248`). Отмена запроса клиентом (Esc) — не сбой: рейтинг не меняется (`local.go:144,157-159,185-188`). Ошибка входа Codex (401) — сбой: она записывается в рейтинг и переводит запрос к следующему члену (`local.go:160,282-283,307-310`).
- **Ограничения:** строка — снимок на момент загрузки страницы, сама не обновляется. Кнопки сброса в шаблонах нет. Маршрут «Anthropic» в рейтинге не участвует.

## 8. Привязка сессий

- **Что делает:** если в запросе есть `metadata.user_id.session_id` (`capture.go:52-66`), первый выбранный член пула закрепляется за ключом sha256(сессия, модель, effort, активный профиль, пул) (`affinity.go:67-82`). Привязка помнит пул и подключение. Пока член здоров, следующие запросы сессии идут к нему, на то же подключение и ту же модель, какими бы ни были рейтинг и нагрузка (`affinity.go:84-127`). После сбоя привязка переходит к члену, который подхватил запрос, и обратно не возвращается (`affinity.go:129-138`, `local.go:166,191`). Отмена клиентом (Esc) привязку не трогает (`local.go:157-159,185-188`). Если у закреплённого члена сменились провайдер или effort или он пропал из пула, привязка сбрасывается (`affinity.go:100-110`).
- **Где настраивается:** отдельных настроек нет; тип пула `balance` распределяет только новые сессии, закреплённые остаются на месте.
- **Код:** `affinity.go:84` (`bindCandidates`), вызов в `local.go:91`.
- **UI/API:** своего интерфейса нет; история группирует запросы по сессиям.
- **Ограничения:** привязки живут только в памяти процесса и теряются при перезапуске: на диск пишется лишь рейтинг (`health.go:183-201`). TTL — 24 ч без активности, не больше 4096 ключей, при переполнении вытесняется самый старый (`affinity.go:94-98,115-124`). Переключение профиля сбрасывает все привязки (`profiles.go:252-254,308-310`). Запрос без `session_id` выбирает модель заново каждый раз.

## 9. Лимиты Anthropic (пассивно)

- **Что делает:** из ответов Anthropic на `/v1/messages`, прошедших через роутер, копирует имена и значения заголовков `anthropic-ratelimit-*` (не больше 64, имя до 128 байт, значение до 256 байт) и время наблюдения. Ответ без таких заголовков отмечается отдельно, ошибки без заголовков игнорируются (`limits.go:260-285,448-464`). Сам роутер к Anthropic за лимитами не обращается, запрос и ответ клиента не меняет (`limits.go:20-25`). Экран `/usage` Claude Code запрашивает лимиты мимо `ANTHROPIC_BASE_URL`, роутер этот запрос не видит (`limits.go:20-22`).
- **Разбор окон:** одна функция, без списка известных имён: `anthropic-ratelimit-<окно>-<поле>`, поле — часть после последнего дефиса (`limits.go:524-592`). `utilization` — доля от 1: `used_percent` = доля × 100, `remaining_percent` = 100 − `used_percent` в пределах 0–100, оба округлены до 0,1. Без `utilization` остаток в процентах считается из `remaining` и `limit` (целые, `limit` > 0). `reset` — unix-секунды или RFC 3339, приводится к UTC; миллисекунды не угадываются. `status` берётся как есть. Заголовок другого вида или значение, которое не разбирается, попадает в `raw` под полным именем (`limits.go:594-613`). Что окна подписки называются `unified-*`, а их шкала — доля и unix-секунды, взято из клиента Claude Code; на живом трафике — не проверено (`limits.go:25-27`).
- **Свежесть:** `fresh` — заголовки видели не больше 30 мин назад; `no_headers` — свежий ответ пришёл без заголовков; `unavailable` — наблюдений нет или они старше 30 мин (`limits.go:31,466-507`).
- **Где настраивается:** `ROUTER_ANTHROPIC_LIMITS_FILE`, по умолчанию `limits.json` рядом с бинарём; пустое значение — только память (`limits.go:179-187`). Запись идёт в фоне: состояние сливается с файлом под `flock` на `limits.json.lock` (ожидание до 2 с), побеждает более новое (`limits.go:231-256,393-443`). Значения лежат только в `limits.json`: в `history.jsonl` их нет, а `router.log` получает лишь имена, по строке на каждый новый набор, не больше 16 наборов за жизнь процесса (`limits.go:287-320`).
- **Код:** `limits.go:448` (`observeResponse`, подключён в `main.go:222-224`), `limits.go:468` (`view`), `limits.go:530` (`parseLimitWindows`).
- **UI/API:** `GET http://127.0.0.1:8788/api/limits`, `Cache-Control: no-store`: лимиты Anthropic и Codex в одном формате (`limits.go:69-170,509-522`):

  ```json
  {"sources":[{"source":"anthropic","state":"fresh","observed_at":"2026-09-25T10:00:00Z","age_seconds":90,"max_age_seconds":1800,
               "raw":{"anthropic-ratelimit-unified-representative-claim":"five_hour"}},
              {"source":"codex","provider":"codex","state":"fresh","observed_at":"2026-09-25T09:58:30Z","age_seconds":180,"max_age_seconds":1800}],
   "windows":[{"source":"anthropic","name":"requests","remaining_percent":90,"remaining":45,"limit":50,"reset_at":"2026-09-25T10:01:00Z","observed_at":"2026-09-25T10:00:00Z"},
              {"source":"anthropic","name":"unified-5h","remaining_percent":77,"used_percent":23,"reset_at":"2026-09-25T12:00:00Z","status":"allowed","observed_at":"2026-09-25T10:00:00Z"},
              {"source":"codex","provider":"codex","name":"primary","remaining_percent":80,"used_percent":20,"reset_at":"2026-09-25T13:00:00Z","window_seconds":18000,"observed_at":"2026-09-25T09:58:30Z"}]}
  ```

  `sources` — сначала `anthropic`, затем по источнику `codex` на каждое подключение Codex, а без них один `codex`; `windows` — всегда список, пусть пустой. У источника всегда есть `source`, `state` и `max_age_seconds`; у `codex` ещё `provider` — имя подключения, если оно есть; `observed_at` и `age_seconds` — время и возраст последнего наблюдения, если оно было, в том числе устаревшего. Окна источника попадают в `windows` только при `state` = `fresh`. У Anthropic `state` — `fresh`, `no_headers` или `unavailable`; `raw` есть только при `fresh`, и тогда всегда, пусть пустой. Поле окна есть, только если оно известно: `source`, `provider` (у окон Codex), `name`, `remaining_percent`, `used_percent`, `remaining`, `limit`, `reset_at` (RFC 3339, UTC), `status`, `window_seconds`, `observed_at`. Источник `codex` описан в разделе 10. В UI `/settings#anthropic-limits` по каждому окну показаны остаток в процентах с полосой, использовано, счётчики, статус, время сброса и сколько до него осталось; окно с остатком до 10% или со статусом `rejected` выделено. Прочие заголовки — под «Другие заголовки», внизу — когда получены данные и сколько они действительны (`ui/settings.html:56-70`).
- **Ограничения:** смысл заголовков подписки не проверен (выше). Числа — на момент последнего ответа Anthropic, а не текущие. Без свежего трафика по маршруту «Anthropic» состояние — `unavailable`, и последнее число не показывается. При остановке `main` не вызывает `close()`, который дописывает отложенное сохранение (`limits.go:370-388`).

## 10. Лимиты Codex

- **Что делает:** для каждого подключения Codex отдельно показывает email, план, ID, окна лимитов (остаток в %, время сброса), дополнительные лимиты и число кредитов сброса. В сеть уходит только `GET https://chatgpt.com/backend-api/wham/usage`: при старте роутера и раз в 10 минут — по очереди для каждого подключения из текущих настроек, — а также по кнопке «Обновить лимиты» (`codex_usage.go:17,148-183,320-385`, `main.go:200`). Неудачный запрос оставляет прежние числа и добавляет к ним текст ошибки; повтор — на следующем цикле, досрочных запросов нет, тики во время запроса отбрасываются (`codex_usage.go:353-377`). Открытие страницы и `/api/limits` читают кеш подключения (`codex_usage.go:264-318`, `limits.go:511-517`).
- **Где настраивается:** `/settings#codex-subscription`, блок на подключение; кнопка «Лимиты Codex» в полосе статуса (`ui/layout.html:82`).
- **Код:** `codex_usage.go:402` (`settingsCodexUsage`), `:422` (`usageCache`), `:264` (`get`), `:200` (`decodeCodexUsage`), `:340` (`codexUsageTargets`), `:358` (`refreshCodexUsageEvery`); `limits.go:123` (`limitsReportOf`).
- **UI/API:** `GET /settings/codex/usage?provider=<имя>` читает кеш, `POST /settings/codex/usage` с `provider` запрашивает OpenAI (`ui.go:141-142`). В `GET /api/limits` (раздел 9) у каждого подключения Codex свой источник `codex`, в порядке `providers.json`; поле `provider` — имя подключения. Без подключений Codex источник `codex` один, без `provider`, в состоянии `not_connected`. `state` — `fresh`, если последний успешный запрос не старше 30 мин, `unavailable`, если его не было или он старше, `not_connected` без входа в это подключение; `error` — текст последней ошибки, в том числе рядом со свежими числами. Окно: `provider` — имя подключения, `name` — `primary`, `secondary` или `<limit_name>-primary`/`-secondary` для дополнительных лимитов, `window_seconds` — длина окна, `status` — `rejected`, если лимит исчерпан или запрещён (`limits.go:118-170`, `codex_usage.go:215-222,235-241`).
- **Ограничения:** кеш живёт только в памяти, у каждого подключения свой (ключ — имя и `auth_id`, `codex_usage.go:420-435`), привязан к аккаунту и сбрасывается при его смене (`codex_usage.go:273-276,293-298`). Лимиты показаны для всего аккаунта, а не только для запросов через роутер. Автообновление идёт, пока есть вход в подключение, даже если страницу никто не открывает. Подключения опрашиваются по очереди, до 15 с на каждое, так что медленное задерживает следующие. Пока идёт запрос, страница и `/api/limits` ждут кеш этого подключения (`codex_usage.go:264-266,361`). Редиректы запрещены, ответ — не больше 1 МиБ (`codex_usage.go:162,174-177`). После cutover автообновление идёт только в активном слоте (раздел 14).

## 11. История запросов

- **Что делает:** каждый запрос `/v1/messages` на любом маршруте, включая отклонённые, попадает в кольцевой буфер. После завершения он дописывается строкой в `history.jsonl` (0600, в файле есть промпты). Когда строк становится больше удвоенного размера буфера, файл перезаписывается только буфером (`main.go:264-272`, `capture.go:147-162,260-283`, `history.go:74-105`). Ответ копируется в буфер до 8 МиБ и не задерживает отдачу клиенту (`main.go:21,267`, `capture.go:234-249`).

Для локального маршрута ещё `OpenAIBody, TrimBefore, TrimAfter, TrimNotes, Served, Attempts[{Model,Err,Dur}]`. Результат: `Status, RespCT, RespBytes, RespTruncated, Resp{Blocks,StopReason,Usage,Model,Error,Note,Events}`.
- **Где настраивается:** `ROUTER_UI_HISTORY` — размер буфера, по умолчанию 300; `ROUTER_UI_HISTORY_FILE` — путь к файлу, пустое значение — только память (`main.go:97`, `history.go:16-24`).
- **Код:** `capture.go:260` (`finish`), `history.go:27` (`load`), `ui.go:289` (`list`), `ui.go:378` (`detail`).
- **UI/API:** `/` — список по сессиям с деталями; `GET /requests?q=&route=&model=&session=&limit=`, `GET /requests/{id}?view=structure|sent|response|raw`, `/requests/{id}/request.json|sent.json|response.txt`, `POST /requests/clear`, полоса статуса `GET /status` (`ui.go:117-124`).

## 13. Каталог моделей

- **Что делает:** каталог хранится в `providers.json`, а не в `models.json`, где лежат рейтинги (раздел 7). В нём `providers` (имя, тип, `base_url`, `api_key`), `models` (`provider/model`) и `catalog` (ID моделей Anthropic, каталоги провайдеров с уровнями effort, `codex_seen`) (`providers.go:19-61`, `catalog.go:20-37`). Каталог обновляется при старте и раз в час: ID Anthropic разбираются со страницы platform.claude.com/docs/en/models/overview, у провайдеров запрашивается `GET {base_url}/models`, у Codex берётся каталог аккаунта с `supported_reasoning_levels` (`catalog.go:84-191`, `ui.go:1281-1374`). Если обновление не удалось, остаётся прежний каталог и появляется заметка (`catalog.go:150-166`). Новая версия Codex попадает в каталог и в те пулы, где уже есть более ранняя модель того же варианта; effort она наследует от неё, если каталог его подтверждает. Модель, удалённая вручную, обратно не добавляется (`catalog.go:196-304`).
- **Как добавить модель:** `/settings#connections` → «Модели и подключение» у провайдера → выбрать модель из списка, который отдаёт провайдер (`POST /settings/models op=add`, `ui.go:1521-1526`), затем включить её в пул или назначить напрямую. - **UI/API:** `POST /settings/refresh-models`, `GET /settings/provider?name=`, `POST /settings/providers op=add|update|remove`, `POST /settings/models op=add|remove` (`ui.go:135-144`).
- **Ограничения:** список ID Anthropic зависит от HTML-разметки страницы документации; при пустом каталоге используется встроенный список (`providers.go:47`, `ui.go:606-609`). Удаление модели или провайдера выключает прямые маршруты на неё и убирает её из пулов всех профилей (`ui.go:1527-1544,921-952`, `profiles.go:89-120`). При добавлении проверяется только формат ID и наличие провайдера (`providers.go:167-186`).

## 14. Деплой и надзор за процессом (launchd, blue/green)

Ссылки этого раздела указывают на коммит 1cd4eec, кроме ссылок на `router` и `internal/cli/`: те — на код после переноса команд службы в бинарь.

- **Что делает до cutover:** `./router install` собирает бинарь и запускает `localrouter install`. Тот гасит роутер, запущенный вручную, пишет LaunchAgent `com.claude-local-router` (RunAtLoad, KeepAlive, ThrottleInterval 10 с, ExitTimeOut 960 с, вывод в `router.log`), загружает его и ждёт `/healthz` (`router:79-83`, `internal/cli/service_cmd.go:180-210`). Уже загруженный агент выгружается и загружается снова, `kickstart -k` не используется. Выгрузка — `bootout` и ожидание, пока `launchctl print` не перестанет находить агент, то есть пока роутер не выйдет: он дослуживает запросы в работе до `ROUTER_DRAIN_TIMEOUT` (900 с), через ExitTimeOut launchd его убивает. Ждать дольше 17 мин команда не станет и тогда завершится с ошибкой (`internal/cli/service_cmd.go:147-163`). Агент, установленный без ExitTimeOut, получает его при следующем `./router install`; до того launchd убивает роутер через свой срок по умолчанию. `start`, `stop`, `status`, `uninstall` и `env` скрипт тоже передаёт бинарю (`router:62-68`). `restart` — сборка, `localrouter stop`, пауза 0,5 с и `localrouter start`; установленный агент при этом выгружается и загружается (`router:69-74`). `start` у загруженного агента только ждёт `/healthz`. Без агента роутер запускается фоновым процессом с `router.pid` (`internal/cli/service_cmd.go:226-262`). Если бинаря нет или он старше скрипта, `start` его пересобирает, а `stop`, `status`, `uninstall` и `env` отказывают с «run ./router build»: старый бинарь принял бы команду за запуск сервера (`router:26-35`). `claude-local` запускает роутер через `router start`, если `/healthz` не отвечает (`claude-local:19-20`).
- **Переход на слоты (cutover):** `./router install --cutover` — единственный переход с агента на Caddy и слоты blue/green (`router:47-60`, `cutover.go:52`). Он требует Caddy, поднимает blue в режиме standby, печатает план и ждёт набранного `yes`. Затем ждёт, пока в `/status` старого UI не останется запросов в работе (`-wait`, 15 мин), останавливает агент и поднимает Caddy на публичных адресах (`cutover.go:69,228-245`). Если Caddy или blue не ответили за `-ready-timeout` (30 с), Caddy и blue останавливаются, а агент возвращается (`cutover.go:70,129-135,210-220`). Адреса слотов, адрес админки Caddy и путь к Caddy сохраняются в `deploy.json`. Повторный cutover отказывает; если переключение прошло, а записать его не удалось, повторный запуск только записывает его (`cutover.go:78,105,201`).
- **Деплой:** `./router deploy` собирает кандидата и поднимает его в другом слоте в режиме standby. Дождавшись ответа, берёт снимок сессий у старого слота, переводит старый слот в quiesced, активирует новый и переключает Caddy через `/load`, не перезапуская его (`router:37-45`, `deploy_controller.go:103-222`). Одинаковый бинарь — no-op; `-force` и `./router restart` после cutover переключают и его (`router:70`). До переключения любой сбой откатывается: старый слот снова активен, новый выгружен (`deploy_controller.go:150-168`). Запрос в работе дослуживает на старом слоте до конца или до `-drain-timeout` (15 мин). Потом слот выгружается, а оставшиеся запросы обрывает его собственный `ROUTER_DRAIN_TIMEOUT` (`deploy_cmd.go:97`, `deploy_controller.go:245-277`, `server.go:159-170`). Деплой, прерванный до переключения, доделывает следующий (`deploy_controller.go:122-148`).
- **Общее состояние:** пишет только активный слот (`lifecycle.go:65`). Миграции конфигурации выполняются при активации, когда старый слот уже не пишет (`server.go:75-89`). Фоновые задачи (перечитывание конфигурации, проверки моделей, каталог, лимиты Codex) стартуют после переключения (`server.go:64-71,90-93`, `runtime.go:55-62`). POST в UI неактивного слота отклоняется, поэтому вход в Codex на 127.0.0.1:1455 возможен только в активном (`ui.go:142`). Кнопка «Подключить Claude» пишет публичный адрес, а не адрес слота (`claude_proxy.go:48`, `deploy_ops.go:225`).
- **Лимиты Codex:** автообновление живёт только в активном слоте; слот в quiesced или draining в Codex не ходит (`codex_usage.go:349-379`).
- **Где настраивается:** `ROUTER_HOME`; файл `env`, откуда скрипт читает `ROUTER_LISTEN`, а cutover — адреса слотов (задать их до cutover, если адреса из `env.example` заняты); после cutover — `ROUTER_HOME/deploy.json`.
- **Код:** `router`, `claude-local`, `internal/cli/service_cmd.go:76` (`Commands`: install, uninstall, start, stop, status, env), `internal/platform` (launchd), `cutover.go:52` (`runCutover`), `deploy_cmd.go:89` (`runDeploy`), `deploy_controller.go:103` (`deploy`), `deploy_ops.go:145` (`caddyfile`), `:222` (`slotPlist`, теперь `slotSpec`), `runtime.go:25` (админка слота), `deploy/check.sh`.
- **UI/API:** `GET /healthz` на публичном адресе. Админка слота — `POST /admin/snapshot|quiesce|activate|drain|compact`, только с loopback (`runtime.go:25-70`). `./router status` показывает активный слот и состояние агентов Caddy, blue и green (`internal/cli/service_cmd.go:458-481`), `./router logs` — лог. `deploy/check.sh` проверяет деплой под настоящими launchd и Caddy на своих каталоге, портах и метках; с `--live` он деплоит сборку, которую запускает активный слот, а не рабочую копию (`deploy/check.sh:184-188`).
- **Ограничения:** до cutover перезапуск держит порт закрытым, пока старый процесс дослуживает запросы и пока новый поднимается; запрос дольше `ROUTER_DRAIN_TIMEOUT` обрывается. Cutover — окно обслуживания: между остановкой агента и стартом Caddy соединения могут не пройти. После cutover `./router install` и `uninstall` отказывают (`internal/cli/service_cmd.go:181-183,213-215`), а `./router stop` выгружает Caddy и оба слота — это простой, а не шаг деплоя (`internal/cli/service_cmd.go:434-454`). Надзор есть только с launchd, то есть на macOS. При остановке `settings.json` не откатывается (раздел 1). `deploy/check.sh --live` на установленном роутере — не проверено.

## Как дополнять

- PR, который меняет поведение, в том же PR правит соответствующий раздел: текст, ссылки `файл:строка`, строку «Состояние на».

- Что не видно из кода, помечать «не проверено» и не додумывать.
- Когда ветка из «В работе» сливается, её строку заменяет раздел возможности.
