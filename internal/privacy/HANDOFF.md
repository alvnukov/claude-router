Команда race (без ложного утверждения, что весь репозиторий проверен под race):

```sh
go test -race ./internal/privacy/... \
  -run '^(TestTwoEngines|TestMapUnique|TestAutoEntries|TestPseudonymNeverCollides|TestSessionsUnlinkable|TestNoSessionScope|TestForeignPseudonymRemasked|TestPruneSessions|TestIssueLockAcrossSessions|TestTouchOnUse|TestResumeWithoutDictionaryRejected|TestEntryPseudonymUnique)$' \
  -count=1
```

Полный прогон содержит 10k сгенерированных пар логин/пароль, 100k выдач
псевдонимов, старый корпус и контекст около 4.2 MB. Fuzz ограничен JSON rewrite;
он не доказывает безопасность всей цепочки. Найденный seed, где строка-замена
состояла из половины UTF-8 руны, сохранён в `testdata/fuzz`. Фильтр правильно
отклонял такую правку; уточнён инвариант fuzz-теста: недопустимый span должен
давать отказ, а не считаться допустимой заменой.

CLI использует синтетические fixtures. Golden-файлы в корневом
`testdata/privacy/golden/` получены с фиксированным **тестовым** ключом и
проверяются повторным запуском. В production ключ случаен.

### Производительность: зафиксированный незакрытый пункт

Команда:

```sh
go test ./internal/privacy -run '^$' \
  -bench '^(BenchmarkMaskRepeatedContext|BenchmarkMask1MB)$' -benchtime=1x -benchmem
```

Результат одного измерения (не p95 и не нагрузочная гарантия):

| Сценарий | Время/op | Allocated bytes/op | Allocs/op |
|---|---:|---:|---:|
| Повторный контекст около 21 KB, готовая сессия | 68.812 ms | 1184656 | 514 |
| Около 1.05 MB, первая выдача сессии | 3596.193 ms | 65304504 | 663 |

Allocated bytes — суммарные выделения, **не** пиковый RSS. Порог старого плана
20 ms на 1 MB не выполнен. Владелец явно отложил highload в пользу рисков;
не заменять этот факт заявлением о производительности или 2000 RPS.

## Независимое ревью

Два независимых прохода по навыку `code-review`, который вызванный `implement`
требует в конце. Исходная точка — переданный владельцем WIP-коммит выше; проверялись
также untracked-файлы. Далее — отдельные оси, без смешения оценок.

### Standards

Три подтверждённых P1-дефекта, исправлены и повторно проверены рецензентом:

1. Unicode case folding (`K`/`K`) приводил к panic из-за байтового среза.
   Теперь граница вычисляется по фактически совпавшим рунам.
2. Повторный Open с тем же явным псевдонимом считал собственное сохранённое
   соответствие коллизией. Теперь оно допускается, чужая выдача отвергается.
3. Диагностика содержала чувствительное имя/адрес. В проверенных отказах
   оставлены структурный путь и безопасная причина.

Постоянные проверки: `TestReviewRegressions/unicode-fold`, `reopen-explicit`,
`safe-errors`; рецензент повторно получил PASS. Существенное ограничение явных
псевдонимов — безопасный отказ при выдаче другой форме/сессии — описано в SPEC.

### Spec

Три исходных P1-дефекта и одна обнаруженная повторным ревью P2-регрессия:

1. Известный секрет без метки, base64-контейнер и `token=base64(...)` проходили
   фильтр. Добавлены проверки известных токенов до/после декодирования.
2. Правило kind терялось между history, JSON-ответом и SSE. Пути нормализованы.
3. Повреждённая секретная ссылка в типизированном поле считалась обычной строкой.
   Теперь требуется целая точная ссылка ожидаемого типа.
4. Строгая проверка нарушила `allow` при восстановлении. Исключение проверяется
   до требования ссылки; `TestAllowedTypedValueRoundTrip` закрепляет симметрию.

Первые три исправления повторно проверены рецензентом; четвёртое закрыто
постоянным регрессионным тестом и финальным полным прогоном.

Итог по осям: Standards — 3 исправлено (наибольшая тяжесть: panic на валидном
Unicode); Spec — 4 исправлено (наибольшая тяжесть: пропуск известного секрета).
Нулевой остаток этих находок не означает нулевой остаток всех рисков.

## Следующие небольшие этапы

1. **Доревью фильтра на новых корпусах.** Приоритет: альтернативные записи IP,
   IPv4-mapped IPv6/zone/IDNA/Unicode normalization; связи разных aliases одной
   личности; имена в структурных идентификаторах и непрозрачных полях; новые
   секреты и контейнеры. Добавлять независимые ожидаемые результаты, не ослаблять
   имеющиеся защиты ради зелёного статуса. NER отдельно оценивать по false
   negatives; не выдавать его отрицательный результат за доказательство.
2. **Семантика сетевых операций.** Решить противоречие старого CIDR-правила и
   отдельно записанного host address; определить работу с новым адресом,
   корректировкой подсети и уже известной, но ошибочно выбранной целью. До этого
   не включать прозрачное исполнение команд на реальном оборудовании.
3. **Ускорение без изменения результата.** Сначала profile на согласованном
   корпусе. Устранить повторный parse/detection; затем ограниченный кэш чистой
   классификации текста с ключом policy+тип+сессия/поколение, не кэшировать
   отрицательные результаты, зависящие от новых секретов или сущностей. Отдельно
   оценить индекс сессий вместо чтения всех файлов под общим lock. Измерить RSS,
   времена cold/warm и повторный контекст нужного токенизатора.
4. **Отдельная P2-интеграция.** Авторизация session_id, смена поколений, судьба
   старых словарей, подписанный thinking, error-to-model retry, атомарность
   инструментальных блоков, остальные HTTP-каналы, отсутствие fallback в
   незамаскированную отправку. Исполнитель/sandbox — вне текущей работы.
5. **Сведение с main и UI.** Эта ветка намеренно не перебазирована поверх
   параллельной работы. Просмотреть актуальный main перед интеграцией; основные
   точки возможного конфликта — регистрация CLI и docs/features.md. Пакет leaf.

Не переносить в следующую сессию предположение, что все plaintext в tool outputs
или все семантические личности уже покрыты. Текущая гарантия ограничена
распознанными сущностями, поддержанными носителями и правилами из SPEC.
